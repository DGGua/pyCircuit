Three archetypes

三个样例，解释两种相反结果

Counter：固定框架成本

C++ 快 4.53×

逻辑很浅，C++ 的直接 comb/tick/transfer 调用成本低；Verilator 的 trigger、settle、NBA 与运行时收尾成本无法被有效摊薄。

BF16 FMAC：大组合网表

Verilator 快 3.19×

C++ gprof 热点有超过 75% 落在组合块。Verilator 能对 RTL 做更成熟的常量传播、wire folding、表达式合并和内联。

SW5809S：组合 + 状态提交

Verilator 快 3.19×

C++ model 同时付出整网表组合求值和 16 个 FIFO 的 tick_compute/tick_commit 成本，字段化状态也限制了宿主编译器的全局优化。

CppEmitter → native C++ model

轻量直接调度，小模型优势明显；复杂模型中，大量字段 load/store、组合块和状态提交可能阻挡跨操作优化。

VerilogEmitter → Verilator C++

有统一 eval/trigger/settle 固定成本；设计变大后，成熟的 RTL 全局简化与紧凑求值逐渐占优。

Counter：Verilator 做得更多

每周期指令数是 C++ 的 3.57×。perf record 中约 60.8% 的周期样本落在由 VlDeleter::deleteAll 路径触发的 pthread mutex lock/unlock。

复杂模型：C++ model 做得更多

BF16 与 SW5809S 的 C++ 指令数分别是 Verilator 的 2.47× 和 3.09×；SW 的分支和 L1D load 还分别多 3.75× 和 3.31×。

全量结论：最大 L1D miss rate 仅 0.0169%，最大 branch miss rate 为 0.933%。主要问题不是 cache 装不下，而是动态指令、字段 load、调度和状态提交工作量。两个“指令更少却更慢”的例外是 calculator 与 digital_filter，原因是 C++ IPC 明显更低。下载 60 行完整 perf 数据。

Engineering direction

下一步优化建议

遵守 pyc4.0 的 gate-first 原则：语义与优化应进入 dialect/MLIR verifier 和 pass，而不是只在某个 emitter 中增加特殊修补。

建立分层性能门禁

保留小型、组合密集、状态密集、FIFO 密集四类代表用例，持续记录 cycle/s、生成代码体积和热点结构。

在 MLIR 层减少无效工作

优先调查组合区域融合、临时信号消除、live-cone pruning，以及无变化周期的组合求值跳过。

降低字段化带来的内存往返

让可局部化的 SSA 值保持为局部表达式，减少每个 op 都落入 model field 后产生的 load/store 与别名阻碍。

优化状态提交协议

针对 FIFO 和寄存器阵列评估 dirty-state、局部 commit 与更紧凑的 current/next 表示，同时以 verifier 保证时序语义。
